# 知識基盤 利用ガイド（人間向け）

> エンジニアでなくても使える知識基盤の使い方。git・GitHubの知識は不要。覚えることは「**AIに聞く・出典のDrive原本を読む・Drive原本を書く**」と、制限情報を置ける場所だけ。
>
> （テンプレート注記: `[管理者名]` を自組織の値に置換し、必要なら削って配布する。「管理者」= 導入責任者（DRI）のメンバー向け呼称）

## まず大前提

- Google Driveには、人間が作る原本と組織の既存アクセス権限がある
- repoには、合意済みAI利用規範と非機微な派生状態がある。区分3・4の詳細は置かない
- メンバーが普段使うのはDriveとAI。repo層は導入DRIとAIが保守する

## 動線1: 聞く（いちばんよく使う）

**AI に日本語で聞くだけ。** 例:

- 「○○プロジェクトの今の論点は？」
- 「進行中のプロジェクトを一覧して」
- 「データの投入ルールってどうなってた？」

AIは、現在の利用者が開けるDrive原本と非機微な派生状態を検索し、Drive原本リンク付きで答える。原本事実と推論を分け、根拠がなければ不足を明示する。**探す作業は人間の仕事ではない。**

## 動線2: 原本を読む

回答に含まれるGoogle Driveリンクを開く。Driveが通常メンバー向けの閲覧画面で、スマホでも使える。

- 特に決定・日付は、回答が原本に裏付けられているか確認する
- リンクが開かない場合は文書オーナーへ確認し、AIに権限回避を求めない
- AI利用規範は、導入DRIまたは承認済みAIに合意済みLayer 1の出典を求める

## 動線3: 原本を書く

承認済みGoogle Drive領域で原本を編集・作成する。現在の共有境界が見えるよう、PJの既存フォルダに置く。例: 会議メモへ決定を記録する、PJ概要を更新する。

v0.1ではAIがDrive原本を自動上書き・削除しない。AIに更新案を作らせた場合も、人間が確認してからDriveへ反映する。AI利用規範の変更だけは別で、[管理者名]へ送りrepoの合意手順を使う。

### 書くときの作法（3つだけ）

1. **承認済み領域を使う** — 選択した共有ドライブまたはフォルダ内に原本を置き、そのアクセス規則に従う
2. **決定と日付を残す** — 古い決定の文脈を黙って消さず、日付付き訂正を追記する
3. **明確なオーナーを置く** — 各PJフォルダまたは主要原本に、鮮度と権限を確認できるオーナーを置く

## 置いてはいけない場所・もの（ここだけは暗記）

- パスワード・APIキー・OAuth token・recovery code（Driveにもrepoにも置かない）
- 区分3・4の情報をrepo、PR本文、issue、共有AIチャット、広く共有されたDriveフォルダへ置くこと
- 情報の承認区分より広い人が見られるDriveフォルダへの保存
- 制限原本の詳細を保持したAI出力を、原本の権限境界外へ移すこと

制限情報を置けるのは、組織の合意済みデータ分類に合い、アクセス範囲が承認されたDrive領域だけ。迷ったら**移動・共有せず[管理者名]に確認**する。

## よくある質問

- **Q. GitHubアカウントは必要？** → A. 通常の聞く・読む・書くには不要。承認済みAIとGoogle Driveを使う
- **Q. 出典リンクが開かない** → A. 文書オーナーへ確認する。AIはDrive権限を回避してはならない
- **Q. どこに書けばよいかわからない** → A. PJオーナーまたは[管理者名]に承認済みDrive領域を確認する
- **Q. AIの答えが古そう** → A. 出典原本を確認し、派生状態を更新できるよう[管理者名]へ不一致を知らせる
- **Q. 回答に原本リンクが無い・出典原本と食い違う** → A. その回答は業務に使わない。質問文と回答を添えて[管理者名]へ知らせる。回答はDrive原本の出典付きが前提（動線1）で、原本が回答を裏付けているかの確認は動線2
