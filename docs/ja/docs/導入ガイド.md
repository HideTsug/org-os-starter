# 導入ガイド

> このリポジトリを自組織の「Org-OS」にするための手順。全工程をAI（Claude Code 等）と対話しながら進められる。人間が自分で決めるべき箇所だけ明示してある。

## Step 0: 体制を決める（人間の仕事・30分）

コードより先に、3つだけ決める。

1. **導入責任者（DRI）** — このリポジトリの管理者。マージ権限を持ち、規範の起案を主導する。AIツールに一番慣れている人が適任（エンジニアである必要はない）
2. **承認体制** — `layer1/` の規範が「効力を持つ」ために誰の合意が必要か。推奨は**経営責任者＋導入責任者＋システム責任者の連結判断**（2〜3名。1人で兼務してもよいが、経営判断とAI技術判断の区別は保つ）
3. **最初の一点突破ユースケース** — 推奨は「プロジェクト知識の横断整理＋対話キャッチアップ」。組織で「あれどうなってたっけ？」が一番起きている領域を選ぶ

決めたら [運用規約](governance/運用規約.md) の権限設計節に記入する。

同じ作業の中で、テンプレートの上流専用項目を片付ける。項目一覧と各項目の扱いは [CLAUDE.md](../CLAUDE.md) の「上流リポジトリ専用の規約」節にある。

## Step 1: Layer 1 の3文書を充填する（AIと対話・1〜2週間）

`layer1/` の3テンプレートを自組織用に充填する。**完璧を待たない** — 充填できる箇所から埋め、経営判断が要る箇所は責任者フラグ `(要・代表)` で残したまま `draft` として運用を始めてよい。

| 文書 | 充填の中心 | 特に業種依存が強い箇所 |
|---|---|---|
| [組織CLAUDE.md](../layer1/組織CLAUDE.md) | 組織方針・判断優先順位・業法コンプラ | コンプライアンス規範（業法・資格法・守秘義務の条文確認） |
| [データ分類マトリクス](../layer1/データ分類マトリクス.md) | データ4区分の具体例・実行環境の棚卸し | 区分4（規制対象）に何が入るか |
| [禁止用途リスト](../layer1/禁止用途リスト.md) | 絶対禁止の具体化 | 専門家責任・独占業務まわり（士業・医療・金融は必須） |

充填のコツ:

- AIに「うちは○○業。この文書の業種依存箇所を、うちの業法に合わせて充填する叩き台を作って。**条文は必ず原文を確認して**」と頼む（AI任せにせず、最終確認は有資格者・責任者が行う）
- 迷った区分は**重い方に倒す**。緩和は運用実績を見てから
- 3文書が `proposed` になったら承認体制で合意し、frontmatter を `status: agreed` に昇格 ＋ 改訂履歴に合意日・合意者を記録。**ここから規範として効力を持つ**

**暫定運用ルール（agreed 昇格まで）**: AI投入は「公開」区分（架空ケース・公開情報）のみ。この暫定ルール自体を先にメンバーへ周知する。

### 合意した3文書を各エージェントの自動ロード経路に結線する

`agreed` への昇格は合意の記録であって、それだけではどのエージェントのコンテキストにも規範が入らない（`layer1/` を自動で読み込む機構は存在しない）。規範を効力ありとして扱う前に、組織が実際に使う**すべての**エージェント型AIの自動ロード経路へ3文書を結線する。手段は各ツールが提供するもの（リポジトリルートの `CLAUDE.md` からの参照・`AGENTS.md`・rules ファイル・プロジェクト指示ファイル・システムプロンプト等）を使う。Drive とチャットAIしか使わないメンバーも対象で、そのエージェントにも同じ経路が要る。

受入基準（エージェントごとに、ファイルを添付しない新規セッションで1回確認する）: 「この作業に適用される[禁止用途リスト](../layer1/禁止用途リスト.md)の項番を引用して」と聞く。合意済み文書の項番が返らないうちは、そのエージェントに対して規範は効力を持っておらず、依拠してはならない。対象エージェントと各々が使う経路は [運用規約](governance/運用規約.md) の検証記録節に記録する。

## Step 2: Google Drive領域を1つ接続する

このステップのゴールは情報源に依存しない形で言える — 質問者本人の権限を継承したままAIが参照できる既存の知識境界を1つ接続し、その背後を再編しないこと。**v0.1 がこのゴールを実装しているのは Google Drive のみ。** Google Workspace テナントが無い組織は Step 2 を実施せず、充填済みLayer 1文書と手動保守の `knowledge/` で運用を開始し、[ADR-0001](decisions/ADR-0001-Google-Drive-first-v0.1.md) の再評価条件2に沿って自組織の情報源と反復業務1つを issue で報告する。

Google Drive の場合は [Google Drive運用プロファイル](Google-Drive-運用プロファイル.md)に従い、Drive全体を再編せず既存の知識境界1つを接続する。

1. 共有ドライブまたはトップフォルダ1つと、その配下の進行中PJを3〜5個選ぶ
2. per-user OAuth・読取専用の参照経路を作る。サービスアカウント・domain-wide delegationは使わない
3. 無害なテスト文書を使い、既存派生ノート経由の回答を含む2アカウント権限差テストを行う。権限のないアカウントの回答・出典に制限文書が現れないこと。合格は [Google Drive運用プロファイル](Google-Drive-運用プロファイル.md) の「権限差テストを行う」に従いADRとして記録する
4. 各PJについて`knowledge/projects/_テンプレート.md`から非機微な派生ノートを作り、Drive原本URLと原本群の最新更新日時を記録する
5. PJオーナーが反復質問5件を選び、すべての回答がDrive原本を出典にし、原本更新日または最終確認日を示すことを検証する

**権限差テスト合格かつ適用対象Layer 1が`agreed`になるまで実機密文書を接続しない。** このゲートは両側とも後のセッションから判定できる必要がある — 合意側は frontmatter `status`、テスト側は Step 2-3 で作るADR。区分3・4の詳細はDriveに残し、`knowledge/`、権限外の人と共有するプロンプト、ログ、PR本文、issueへ複製しない。全commit前にAIが機密チェックする（[CLAUDE.md](../CLAUDE.md)参照）。

サンプルノート（`PJ-サンプル-備品管理.md`・`ISSUE-0001.md`）はノートの章立ての見本。Drive由来ではないため、Drive派生ノートに必須の source 系・アクセス系キーをどれも持たない。自組織の派生PJノートが3本入ったら削除してよい。

## Step 3: 日常運用に乗せる（2週間の定着期間）

メンバーには [利用ガイド](利用ガイド.md) を配布する。覚えるのは、AIに聞く・出典のDrive原本を読む・Drive原本を書く、の3動線だけ。

定着のドライバは**DRIが毎日使って見せること**:

- 定例で、AIがDrive原本リンク付きで回答するところを実演する（動線1: 聞く）
- 会議後に、承認済みDrive領域の原本へ決定を記録する（動線3: 書く）
- 週1回、`source_modified_at`と原本を照合し、staleな派生ノートを更新する

2週間時点の判定は、感覚ではなく観測できるもので行う。判定基準は、直近7日間で Step 2-5 で選んだ反復質問5件がそれぞれ1回以上AI経由で問われ、すべての回答が原本をリンクし、その原本の最終更新日または最終確認日を示していること（回答が満たすべき条件の全文は [Google Drive運用プロファイル](Google-Drive-運用プロファイル.md) の「5.『聞く』を検証する」にある）。件数と未達だった質問を [運用規約](governance/運用規約.md) の検証記録節に記録する。Step 2 を実施しなかった組織は、手動保守の `knowledge/` に対して同じ基準を適用する（Drive原本リンクの代わりに最終確認日を示す）。

基準を満たさない場合は、ノートの粒度・鮮度・網羅性のどれが欠けているかを記録し、その箇所を直してから同じ5件で再測定する。基準を1度満たすまで Step 4 に入らない。

## Step 4: 広げる（実運用からの抽出）

Layer 2 が回り始めてから、次を検討する（詳細: [architecture.md](architecture.md) の発展要素）:

- **SKILL化（Layer 3）** — 3回以上繰り返した対話パターン（キャッチアップ要約・議事録取り込み・issue起票）から順に Skill にする
- **Drive change取込（Layer 4）** — Drive change feedから非機微な派生ノートを増分更新する。冪等性とstale処理を必須にする
- **追加情報源adapter（Layer 4）** — Drive外の情報源が反復業務を阻害したと観測された場合だけ1つ追加する。Notion・Slack・Chatwork・SharePointはv0.1コア外
- **監査・レビュー（Layer 5）** — データ分類マトリクスの監査ログ運用を本格化

**広げる判断も「毎日使われているか」を基準にする。** 使われていない層の上に次を積まない。

## カスタマイズポイント一覧

| 箇所 | 初期値 | 変える判断基準 |
|---|---|---|
| 承認体制の人数 | 3名連結判断 | 組織規模。最小構成は「経営1名＋構築1名」の2名 |
| データ区分の粒度 | 4区分 | 規制産業は区分4の細分化、非規制でも4区分の枠は維持を推奨 |
| 実行環境の棚卸し | E1〜E3の3+1環境 | 自組織で実際に使うAIサービスをすべてマトリクスに載せる |
| Drive情報源境界 | 共有ドライブまたはトップフォルダ1つ | 反復質問5件と権限検証が通ってから広げる |
| knowledge/ のノート種別 | projects / issues | 顧客・案件・議事録ノートは Layer 4 と合わせて拡張 |
| 責任者フラグの表記 | `(要・<役割名>)` | 実名でも役割名でもよいが、リポジトリを外部共有する予定があるなら役割名 |
| マージ権限 | DRIのみ | write権限者が増えたら PR 運用 + レビュー必須へ移行 |

## つまずきポイント（実運用からの教訓）

- **規範を後回しにして道具から作る** → 一番多い失敗。データ事故が起きてから規範を作ると信頼回復に倍のコストがかかる
- **5層を横並びで着工する** → どれも中途半端になり「使われないハコモノ」化する。一点突破を守る
- **AIに全部任せて人間が読まない** → 規範文書の最終確認は必ず人間（特にコンプラ規範は有資格者）。AIは叩き台と検索の道具
- **ノートの鮮度が落ちて信頼を失う** → 「AIの答えが古い」と一度思われると使われなくなる。`last_reviewed` の週次確認をDRIの習慣にする
- **フォルダ配置を認可とみなす** → フォルダ名やPJ紐付けに権限付与効果はない。2アカウントで利用者のDrive実効権限を検証する
- **反復利用前に別コネクタを足す** → 利用者が反復質問を挙げられないなら、情報源の広さがボトルネックではない
